## 1. Purpose

This plan is the acceptance gate between "the code builds and the unit suite
passes" and "a paying customer can use the product end to end". It walks every
surface a real user touches — from the first sign-up request, through the
invoice lifecycle, to logout — and states the expected result in testable
terms.

The plan deliberately separates:

- **Blocking acceptance tests** — must pass before a release is announced.
- **Conditional tests** — depend on the customer supplying their own
  infrastructure (AI key, SMTP server, payment gateway, ERP), so they are
  executed with the customer's credentials during onboarding.

## 2. Scope

### 2.1 In scope

1. Public surface: `/login`, `/signup`, `/forgot-password`, `/reset-password`,
   `/accept-invite`, `/track/:token`, `/invoices/track/:token`, legal pages,
   `/forbidden`, `/403`, unknown routes, cookie consent, network-status alert.
2. Account lifecycle: sign-up, first login, session refresh, lockout,
   password reset, invitation acceptance, seat limits, deactivation, logout.
3. Every authenticated page: Overview, Inbox, Invoices, Invoice Detail,
   Exceptions, Approvals, Payments, Suppliers, Purchase Orders, Items,
   Reports, Archive, Notifications, Profile, Bank Accounts, Settings.
4. The full invoice lifecycle: Receive → Capture → Validate → Match →
   Exception → Approval → Payment → ERP Sync → Archive.
5. Settings persistence and the BYO infrastructure cards (AI key, database,
   ERP, payment gateway, email, API keys, billing).
6. Data export and payment file generation.
7. Tenant isolation, role-based access, and financial idempotency checks.
8. Accessibility and design-system compliance on the touched surfaces.

### 2.2 Out of scope for this release (must be stated in the acceptance meeting)

These are known limits, not defects. If a tester reports them as bugs, close
them as "documented limitation".

| Limitation | Customer-visible behaviour |
| :--- | :--- |
| BYODB record routing | Avarta verifies and stores an encrypted PostgreSQL connection; live record routing happens during managed onboarding. CSV export of invoices, suppliers, and payments is available immediately. |
| Live ERP OAuth | Tally/QuickBooks/Xero files can be exported; direct two-way API sync is not connected. |
| Live payout execution | Payment gateway adapters validate credentials against the provider API, but payout execution returns a simulated clearing reference until the tenant's payout credentials and webhook confirmation are enabled. |
| Billing checkout | Plan changes are an authenticated administrator action with an audit record. No card checkout or invoice PDF is generated by Avarta. |
| Notification delivery | The notification feed is real. Automatic email/Slack fan-out on every event is not enabled; the Settings test buttons send a real message through the tenant connector. |
| OCR accuracy | Extraction quality depends on the tenant's AI provider key and document quality. No confidence value auto-writes a field. |

## 3. Test environment

### 3.1 Required configuration

Create `.env` from `.env.example` and confirm:

| Variable | Value used for UAT | Notes |
| :--- | :--- | :--- |
| `NODE_ENV` | `development` | API refuses to boot if unset. |
| `DATABASE_URL` | Dedicated UAT database | Never point UAT at the production Neon database. |
| `DIRECT_URL` | Same as `DATABASE_URL` locally | Required for migrations. |
| `JWT_SECRET` | Random 32+ characters | |
| `APP_ENCRYPTION_KEY` | 64 hex characters | Encrypts BYOK/BYODB/gateway/bank secrets. |
| `WEB_ORIGIN` | `http://localhost:5173` | Must match the web origin or CORS blocks every call. |
| `ENABLE_PUBLIC_SIGNUP` | `true` | Sign-up is fail-closed without it. |
| `MAX_PUBLIC_SIGNUPS` | `5` for UAT | Default is 2. |
| `MASTER_DEV_EMAIL` / `MASTER_DEV_PASSWORD` | Development only | Never set with `NODE_ENV=production`; the API refuses to boot. |

Web `.env`: `VITE_API_URL="http://localhost:4000/api/v1"`.

### 3.2 Bring-up

```bash
pnpm install
pnpm --filter @ap-saas/api db:generate
pnpm db:deploy      # applies migrations to the UAT database
pnpm db:seed        # local development data only
pnpm dev:api
pnpm dev:web
```

Confirm `GET http://localhost:4000/health` returns
`{"status":"ok","database":"connected"}`.

### 3.3 Reset between rounds

1. Create a fresh database (or drop and recreate the schema).
2. Run `pnpm db:deploy` and `pnpm db:seed`.
3. Clear browser storage for the app origin (sessions are in memory plus an
   httpOnly refresh cookie, but stale tabs and theme/consent flags persist).
4. Restart both dev servers to clear in-memory rate-limit buckets.

## 6. Entry, exit, and defect handling

**Entry criteria**

- `pnpm typecheck`, `pnpm lint`, and `pnpm test` pass on the build under test.
- UAT environment is seeded and reachable.
- The five role accounts exist.

**Exit criteria**

- Every blocking case passes, or the failure is accepted in writing by the
  product owner with a severity and a target release.
- No Severity 1 or Severity 2 defect is open.
- Evidence (screenshots, API responses, exported files) is attached to each
  case.

**Severity**

| Severity | Definition | Release impact |
| :--- | :--- | :--- |
| S1 | Data loss, cross-tenant exposure, incorrect money movement, cannot log in. | Blocks release. |
| S2 | A core workflow step cannot complete; incorrect figure shown as confirmed. | Blocks release. |
| S3 | Workaround exists; cosmetic or copy defect. | May ship with a logged follow-up. |
| S4 | Suggestion. | Backlog. |
